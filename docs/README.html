file-org · 설명서와 사용 방법

흩어진 파일을 한 곳으로, 잃는 것 없이

file-org는 로컬·Google Drive·OneDrive·iCloud에 흩어진 파일을 하나의 마스터 폴더 체계로 복구·분류·이관·정리하는 방법과 도구입니다. Claude Code나 Codex 같은 AI 도우미가 읽고 따르는 설명서(SKILL.md)와, 사람이 직접 써도 되는 파이썬 스크립트로 되어 있습니다.

핵심 원칙은 하나입니다. 사용자가 되돌릴 수 없는 일은 하지 않는다. 삭제하지 않고, 덮어쓰지 않고, 모든 변경은 미리 보여 주고 승인을 받은 뒤 실행하고, 끝나면 독립적으로 검증하고 기록합니다.

1언제 쓰나

다음 중 하나라도 해당하면 이 방법이 맞습니다.

  • 같은 성격의 파일이 두 곳 이상에 흩어져 있어 검색이 갈라진다.
  • 클라우드 동기화 폴더(Google Drive, OneDrive, iCloud Drive)가 끼어 있다.
  • 0바이트 파일, 이름만 같은 다른 파일, 내용이 같은 중복 파일이 섞여 있다.
  • 파일 수가 수십 개를 넘고, 잘못 옮기면 되돌리기 어렵다.

파일 하나를 옮기거나 이름만 바꾸는 일에는 쓰지 않습니다. 그냥 하면 됩니다.

2원칙 8가지

각 원칙에는 실제로 겪은 사고나 실패가 하나씩 붙어 있습니다. 규칙이 아니라 교훈입니다.

1. 삭제하지 않는다

이동·복사·격리만 합니다. 중복이나 쓸모없는 파일은 격리 폴더에 모아 두고, 삭제는 사용자가 결정합니다. 그때도 휴지통(30일 복구)을 먼저 씁니다.

검토 시트의 기본값 "삭제"가 그대로 실행돼 633개가 휴지통 기한을 넘겨 영구 소실된 적이 있습니다.

2. 기본값을 실행하지 않는다

사람이 채우거나 승인한 행만 적용합니다. 승인 열이 비어 있으면 그 행은 건너뜁니다.

위 사고의 직접 원인이었습니다.

3. dry-run → 승인 → 적용 → 검증

모든 쓰기는 먼저 결과를 보여 주고(dry-run), 승인 뒤 실행하고, 끝나면 별도 코드로 "목적지 존재 · 원본 소멸 · 크기 일치"를 다시 셉니다.

스크립트 안의 자체 검증만 믿지 않습니다.

4. 덮어쓰지 않는다

같은 이름이 있으면 멈춰서 기록합니다. 내용이 같으면 격리 폴더로, 다르면 이름 끝에 (2)를 붙여 둘 다 보존합니다. 복사도 임시 이름으로 쓴 뒤 바꾸므로 잘린 파일이 남지 않습니다.

5. 경로는 NFC 정규화 후 비교

macOS·iCloud는 한글을 NFD로, Drive·Windows는 NFC로 저장합니다. 같은 이름이 "다른 파일"로 보여 중복 복사나 오판이 생기므로, 비교 전에 반드시 정규화합니다. 셸 glob·find 대신 Python os.walk로 셉니다.

6. 클라우드 파일은 스텁일 수 있다

이름·크기만 로컬에 있고 내용은 서버에 있습니다. 읽는 순간 다운로드되므로 크기·이름 비교를 먼저 하고 해시는 필요한 것만 계산합니다. 디스크 여유 가드(8 GiB)를 둡니다.

10 GB를 "비교만" 하다가 디스크가 찬 적이 있습니다.

7. 분류 근거는 파일명 → 본문 → 사람

규칙으로 못 정한 파일을 "미분류" 서랍에 쌓지 않습니다. 본문 앞 200자를 표로 뽑아 보고, 그래도 안 되면 사람이 읽어 판정하고 묶음 단위로 승인합니다.

934건을 직접 읽는 비용이 규칙을 세 번 고치는 비용보다 적었습니다.

8. 재개 가능하게

계획 CSV에 상태 열, 로그에 모든 행을 남깁니다. 중단되면 같은 명령을 다시 돌려 "대기" 행만 처리합니다.

3작업 흐름: 한 바퀴

작업은 아래 일곱 단계를 한 바퀴로 돕니다. 각 단계는 자체 산출물(CSV·MD)을 남기고, 다음 단계는 앞 단계의 검증을 통과한 뒤에만 들어갑니다. 노란 칸은 사용자의 결정이 필요한 곳입니다.

측정저장소마다 파일 수·용량·0바이트·클라우드 전용 수. 읽기 전용.
제안무엇을 어디로 옮길지 CSV로. 근거와 신뢰도를 함께.
dry-run실제로 옮기지 않고 결과만 출력. 동명 충돌·원본 없음 확인.
승인사용자가 표를 보고 ✓ / ✗ / 대안 경로를 적는다.
적용승인된 행만. 덮어쓰기 없이 같은 볼륨 안 rename 또는 복사.
검증로그를 다시 읽어 목적지 존재·원본 소멸·크기 일치를 센다.
기록moves_v2.csv에 시간·동작·원본·목적지·사유. 산출물은 git 커밋.

큰 정리는 이 바퀴를 단계별로 반복합니다: 측정 → 0바이트 복구 → 구조 수습 → 분류 → 이관(복사) → 로컬 정리 → 남은 결정 목록. 각 전환점에서 멈추고 보고합니다.

4시작하기

설치

Python 3.8 이상이면 macOS·Windows·Linux에서 같은 명령으로 돕니다. 표준 라이브러리만 씁니다.

git clone https://github.com/Noah7601/file-org ~/.claude/skills/file-org
python3 ~/.claude/skills/file-org/tests/smoke_test.py

두 번째 줄은 자체 검사입니다. 임시 폴더에 시험 트리를 만들어 스크립트 네 개를 dry-run → apply로 돌리고 20여 개 항목(NFD 이름, 동명 충돌, 격리, 덮어쓰기 없음, 재개)을 확인합니다. 새 컴퓨터에서는 먼저 이것을 돌립니다. Windows는 py -3로 실행합니다.

Codex를 쓰면 같은 내용을 ~/.codex/skills/file-org에 둡니다. AI 도우미에게 "파일 정리해줘", "Drive·OneDrive·iCloud 합쳐줘", "중복 파일 찾아줘"처럼 말하면 이 설명서가 적용됩니다.

처음 정하는 세 가지

도우미는 시작할 때 이 셋만 묻습니다. 나머지는 측정하면 나옵니다.

  1. 마스터를 어디로 할지. 로컬 폴더든 클라우드든 하나만. Google Drive가 가장 자세히 검증되었습니다.
  2. 삭제를 허용할지. 기본은 불허. 허용해도 휴지통 우선, 영구 삭제는 건별 승인.
  3. 분류를 누가 확정할지. 기본은 "도우미가 제안, 사용자가 승인".

다섯 개 모두 기본이 dry-run입니다. --apply를 붙여야 실제로 씁니다. 새 스크립트를 짜기 전에 이 다섯으로 되는지 먼저 봅니다.

6클라우드 폴더 주의

세 서비스는 폴더처럼 보이지만 폴더가 아닙니다. 아래는 실제로 겪은 실패와 그때 통한 방법입니다. 새 환경에서는 각 항목을 1~2개 파일로 먼저 확인합니다.

서비스함정대처
Google Drive (스트리밍)0바이트 스텁의 rename이 정착하지 않음. 확장자 없는 PDF에 .pdf를 붙이는 등 자동 개명. 로컬 캐시가 디스크를 먹음(16 GiB까지). Windows에서는 클라우드 전용 여부가 속성으로 안 보임.스텁은 옮기지 않고 목록만. 개명은 stem 일치로 정정. 디스크 가드로 막고, 걸리면 "다운로드 제거" 후 재개. 업로드 확인은 xattr(macOS) 또는 웹에서 표본.
OneDrive클라우드 전용 파일을 열 때 Errno 60(타임아웃). 0바이트 원본도 많음.0/15/30/60/120초 재시도. 소스는 크기 > 0만. Windows는 attrib +U -P로 로컬 사본 비움.
iCloud Drive"저장 공간 최적화"가 받아 둔 파일을 몇 시간 안에 다시 비움. rsync는 dataless 파일에서 죽음. Finder 휴지통은 클라우드 전용 항목을 거부(-8013).사전 다운로드 금지. 파일 단위로 읽은 즉시 쓰기. 삭제는 복구 경로(iCloud.com 최근 삭제, 30일)를 사용자가 알고 고르게.
공통 금지: 클라우드 폴더 안에서 rsync --delete, rm -rf, 대량 mv, Windows의 del /s·robocopy /MIR·Remove-Item -Recurse. 셸 glob으로 한글 경로 다루기.

Windows에서는 경로 260자 제한(LongPathsEnabled 또는 \\?\ 접두), 금지 문자(\ / : * ? " < > |), 휴지통 보내기는 PowerShell의 FileSystem.DeleteFile(…, 'SendToRecycleBin')을 씁니다. 세부는 저장소의 references/cloud-fs.md.

7폴더 체계와 이름 규칙

마스터는 "주제 번호 + 이름" 1단계, 그 아래 프로젝트(연도_프로젝트명, 거래처, 연도), 그 아래 종류 폴더로 갑니다. 아래는 한 회사의 예시이고, 번호와 이름은 업무에 맞게 정합니다. 프리랜서라면 30_고객/<고객명>/<연도_건명>, 연구실이라면 40_과제/<연도_과제명>, 정부 지원사업이 많다면 40_지원사업/<연도_사업명>/{신청, 보고, 집행증빙}처럼 씁니다. 바꾸지 않는 것은 번호 붙은 1단계, 00_INBOX, _정리로그 세 가지입니다.

00_INBOX_분류대기/<출처>/<원래 폴더>      판정 못 한 것은 원래 구조 그대로
10_회사_기본/{사업자·법인, 증명서, 인사·노무, 인증·특허}
20_재무_세무/<연도>
30_계약_법무/<거래처>
40_프로젝트/<연도_프로젝트명>/{기획, 보고, 증빙, 자료·양식, 계약·변경, 기타}
   └ 증빙/<비용항목>_<거래처>_<YYMM>/        거래 하나 = 하위폴더 하나(문서세트)
90_미디어/<활동>/<연>/<연-월>
99_Archive
_정리로그/{moves_v2.csv, 격리 폴더들}

판정은 (1) 어느 프로젝트인가 (2) 어떤 종류인가 두 축입니다. 프로젝트를 모르면 종류만 정해 그 프로젝트의 기타에, 둘 다 모르면 INBOX에 원래 구조로 둡니다. "미상"·"미분류" 서랍을 새로 만들지 않습니다.

앞으로 만드는 파일의 이름

  • 증빙은 번호_문서종류_거래처_YYMMDD. 거래 하나는 하위폴더 하나로 두면 폴더가 곧 문서세트가 됩니다. 제출용 zip을 만들어도 낱개 파일은 폴더에 남깁니다(zip 안에만 있던 서류가 "없는 서류"가 된 사례).
  • 초안·개정은 _v1, _v2. "최종", "최최종", "(최종1)", "_2", "(1)"은 몇 판째인지 알 수 없습니다.
  • (2) 접미는 정리 도구 전용. 같은 이름에 내용이 다른 파일이 부딪혔을 때 도구가 붙이는 표시이므로, 사람이 판 번호로 쓰지 않습니다.

단계마다 하는 검증

  1. 스크립트 자체 검증(크기 일치, 존재). 필요조건.
  2. 독립 검증: 로그를 다시 읽어 move·copy 행의 목적지 존재·원본 소멸(copy면 보존)을 센다. 불일치가 0이 아니면 멈추고 보고.
  3. 표본 열어 보기(PDF·HWP·XLSX 5~10개). 0으로 채워진 "복구본"을 잡는 유일한 방법.
  4. 재인벤토리: 목표였던 수치(0바이트 수, 미이관 수)를 같은 코드로 다시 잰다.

보고 형식

단계가 끝날 때마다 ① 결과 한 줄(무엇이 몇 건, 오류 몇 건, 검증 결과) ② 표(대상/건수/비고) ③ 기록(로그 행 수, 산출물 경로, 커밋) ④ 남은 사용자 결정 번호 목록. 예: "복사 3,499/3,499 · 오류 0 · 독립 검증 3,499/3,499 · 업로드 확인 100%."

산출물 폴더는 git으로 관리하고 단계마다 커밋합니다. 커밋 전에 근거 CSV의 주민번호·계좌·전화 패턴을 마스킹합니다. 비밀키·인증서(.key, .p12, 복구키 txt)는 어떤 클라우드에도 올리지 않고 제자리에 두고 사용자에게만 알립니다.

9자주 묻는 질문

삭제는 언제 하나요?

도구는 하지 않습니다. 격리 폴더에 모인 중복·스텁·빈 폴더를 사용자가 Finder·탐색기·웹에서 휴지통으로 보냅니다. 삭제 직전에는 보관본이 실제로 존재하는지 sha1로 다시 대조합니다.

마스터를 OneDrive나 iCloud로 둘 수 있나요?

됩니다. 스크립트는 경로를 인자로 받을 뿐입니다. 다만 업로드 확인 요령과 0바이트 스텁 규칙은 Google Drive에서 겪은 것이 가장 자세하고, 다른 두 서비스는 아직 그만큼 세부가 없습니다.

중간에 끊기면요?

같은 명령을 다시 돌리면 됩니다. 계획 CSV의 상태 열과 로그를 보고 "대기" 행만 처리하고, copy_tree는 크기·수정시각이 같은 파일을 건너뜁니다.

AI 도우미가 스크립트 밖에서 rm을 치면요?

스크립트에는 삭제 호출이 없지만(자기 임시 파일 .part 정리뿐), 도우미가 직접 명령을 칠 수는 있습니다. 설명서는 이를 금지하지만 강제하지는 못하므로 프로그램 쪽에서 두 겹으로 막습니다.

1겹, 삭제·이동 명령 거부. 작업 폴더의 .claude/settings.json(또는 ~/.claude/settings.json)에 넣습니다. 스크립트 실행은 그대로 됩니다.

{
  "permissions": {
    "deny": [
      "Bash(rm:*)", "Bash(rmdir:*)", "Bash(rsync:*)", "Bash(mv:*)", "Bash(unlink:*)",
      "Bash(find * -delete:*)", "Bash(del:*)", "Bash(robocopy:*)", "Bash(Remove-Item:*)"
    ]
  }
}

2겹, 쓰기 범위 제한. Claude Code의 샌드박스(설정의 sandbox 항목 또는 /sandbox)를 켜면 셸 명령이 작업 폴더 밖에 쓰지 못합니다. 이렇게 두면 삭제가 필요한 단계는 도우미가 목록만 보고하고 사람이 직접 하게 됩니다. 정리가 끝나면 거부 목록을 지워도 됩니다.

Windows에서도 되나요?

Windows 11 + Python 3.12에서 자체 검사 28개 항목을 통과했습니다. OneDrive 파일 온디맨드 속성 판정, 260자 경로, 휴지통 보내기까지 확인했습니다. iCloud for Windows는 미검증입니다.

정리가 끝난 뒤에는?

폴더 경로는 "이 네 파일이 한 세트"라는 관계를 담지 못합니다. 그래서 거래 하나를 하위폴더 하나로 두고, 지침의 필수 증빙 목록을 코드로 검사하는 체크기를 돌립니다. 결과는 경고 목록으로만 나오고, 고치는 것은 평소의 제안→승인→적용 절차를 탑니다. 세부는 references/ontology.md.

10용어

마스터
모든 파일이 모이는 하나의 폴더 체계.
스텁
클라우드 전용 파일. 이름·크기만 로컬에 있고 내용은 서버에. 0바이트 스텁은 내용이 아예 없는 것.
dry-run
실제로 쓰지 않고 결과만 출력하는 실행. 모든 스크립트의 기본.
격리
삭제 대신 _정리로그/_이관중복_YYYYMMDD/ 같은 폴더로 옮겨 두는 것. 원래 상대 경로를 유지.
NFC / NFD
한글을 저장하는 두 방식. 보기엔 같아도 바이트가 달라 비교 전 정규화가 필요.
독립 검증
적용 스크립트와 별개로 로그를 다시 읽어 결과를 세는 것.
문서세트
한 거래의 증빙 묶음(견적서·거래명세서·세금계산서·검수확인서 등). 폴더 하나로 두고 체크기로 완결성을 검사.
디스크 가드
여유 공간이 기준(8 GiB) 아래로 내려가면 배치를 멈추는 장치.

두 달 동안 실제 정리(저장소 4곳, 2만여 파일)에서 나온 절차이고, macOS와 Windows 11에서 검증했습니다. 코드·상세 문서: github.com/Noah7601/file-org (MIT)
