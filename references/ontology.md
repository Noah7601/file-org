# 온톨로지 — 정리가 끝난 뒤, 관계를 파일 이동에도 살아남게

실제 정리 프로젝트의 마무리 단계에서 합의한 접근이다. 폴더 경로는 "이 네 파일이 하나의 지원사업A 정산 증빙 세트"라는 사실을 담지 못한다. 그래서 경로가 깨지면(`(1)` 폴더로 갈라지면) 의미도 같이 사라지고 아무 경고도 나지 않는다. 온톨로지는 그 관계를 파일과 별개의 객체로 만들어 두는 일이다.

## 언제 하나 — 순서가 전부다

```
Phase 0  마스터 복구·정리 완료(0바이트 0, 미이관 0)     ← 먼저. 예외 없음
Phase 1  사업 하나만 시범(가장 지저분한 폴더부터)
Phase 2  graphify로 전체 그래프 + 노션 수동 레이어
Phase 3  입구를 노션으로
```

깨진 마스터 위에 온톨로지를 만들면 "깨진 파일을 가리키는 예쁜 그래프"가 된다. 또 이 작업은 설계가 가장 재미있어서 실행 없이 설계만 반복하기 쉽다(운영매뉴얼 → 이관 구조 → 온톨로지, 세 번 모두 설계에서 멈춘 전력). 시범은 폴더 하나로 끝까지 돌려 **실제로 무엇을 잡아내는지** 보고 나서 넓힌다.

## 최소 모델 — 개체 5종, 관계 4개

```
사업        지원사업A, 지원사업B, 지원사업C …       (폴더 <연도>_<사업명>과 1:1)
거래처      거래처A, 거래처B, 거래처C …
문서세트    정산 증빙 세트, 신청 서류 세트 …          ← 사고를 막는 핵심
의무·기한   제출할 것, 마감일, 담당
저장위치    어느 클라우드, 어느 폴더

사업 ─요구→ 문서세트 ─구성→ 파일
사업 ─상대→ 거래처
문서세트 ─보관→ 저장위치
```

더 늘리지 않는다. 개체가 늘수록 유지 비용이 먼저 늘고 가치는 늦게 는다.

## 가치는 지도가 아니라 검증(체크섬)

온톨로지를 **규칙을 거는 자리**로 쓴다.

```
정산 증빙 세트 = 견적서 + 비교견적서 + 거래명세서 + 검수확인서
                 ↑ 하나라도 없으면 경고
협약 세트      = 협약서 + 사업계획서(확정본) + 통장사본
```

이 규칙이 있었으면 비교견적서가 `(1)` 폴더에만 있다는 것을 사람이 아니라 시스템이 발견했다. 규칙 검사는 **코드**가 한다(모델보다 정확하고 재현된다). 검사 결과는 "경고 목록"으로만 나오고, 고치는 것은 평소의 제안→승인→적용 절차를 탄다.

## 세 층 — 누가 무엇을 유지하나

```
파일      무엇이 존재하는가          ← 사실. 마스터 폴더
  ↓ graphify 자동 추출 (--update 로 증분 재생성)
그래프    무엇이 무엇과 엮이는가      ← 기계 생성. 손대지 않는다
  ↓ 선별
노션      상태·기한·판단·근거         ← 사람 작성. 소수 정예
```

- **그래프를 손으로 유지하지 않는다.** 손으로 만든 온톨로지는 6개월이면 썩고, 썩은 온톨로지는 없느니만 못하다. `graphify --update`로 다시 뽑는다. AI와 사람이 같이 보는 창구는 `--mcp`(질의) + `--wiki`(문서) 조합, 노션 임베드는 `--svg`.
- **노션은 중계소가 아니다.** 추론·제약 검사·대량 처리를 못 한다. 파일이 담을 수 없는 것(상태, 기한, 결정 근거, 담당)만 둔다.

## 개체 정렬 — "같은 것인가"를 누가 정하나

중복 개체(`주식회사 한글표기` ↔ `영문약칭`, 운영기관명 ↔ 프로그램명)는 정리 과정에서 계속 나온다. 처리 순서:

1. **코드 규칙 먼저**: 사업자번호·주소·대표자 일치 같은 확정 근거, "둘 다 희박"·"한쪽이 넘침" 같은 구조 규칙.
2. **모델은 제안만**: 쌍마다 `같은 회사인가`(같음/검토/다름) + 보조 예·아니오 질문. 확률을 정직하게 내는 System One 계열(Jev)이 파일 운명이 걸린 판단에 적합하다. "모르겠다"를 0.5 근처로 말하기 때문이다.
3. **라우팅 네 갈래**: 병합권고 → 사람 승인 후에만 병합 / 검토 → 큐(노션) / 관련-병합금지(상하위·조각) / 무관.
4. **성공 기준을 먼저 정한다**: 20쌍을 손으로 라벨링해 대조, 병합권고 정밀도 ≥ 85%, 검토로 빠진 비율 ≤ 30%면 확장. 못 미치면 사람 판독으로 돌아간다.

실측(89쌍 파일럿): 검토 70 · 관련-병합금지 6 · 조각-흡수 5 · 병합권고 2. 즉 대부분은 결국 사람이 본다. 모델은 **읽을 순서를 정해 주는 도구**이지 결정자가 아니다.

| 과제 | 모델 적합 | 이유 |
|---|---|---|
| 중복 개체 병합 제안 | ◎ | 정해진 보기 고르기 + 확률 |
| 분류 쏠림 재조정 | ○ | 5지선다 + confidence로 애매한 건 사람에게 |
| 0바이트 복구 | ✗ | 판단이 아니라 해시·크기 대조 = 코드 |
| 증빙 세트 완결성 검사 | ✗ | 규칙이 있으면 코드가 더 정확 |
| 파일 삭제·이동 실행 | ✗✗ | **어떤 모델도** 직접 실행 금지 |

일회성 정리에는 모델 정렬이 과하다. 동기화 때마다 새 개체가 들어오고 "기존 것과 같은가"를 반복해서 묻는 **계속 도는 시스템**을 만들 때 적합하다. 결정은 그 질문 하나로 귀결된다.

## 정리 작업과의 연결

- 분류 단계의 사업·거래처 사전(`classify.md`의 PROGRAMS/PARTIES)은 이 온톨로지의 개체 목록 초안이다. 폴더 이름(`<연도>_<사업명>`)이 곧 개체 ID가 되도록 유지한다.
- 같은 사업이 두 이름으로 갈라진 사례(운영기관명 = 프로그램명, 영문 약칭 = 정식 사업명)는 개체 정렬의 첫 입력이다. 병합은 본문 근거 2건 이상 + 사용자 승인.
- 정리가 끝난 마스터에서 `graphify`를 돌려 그래프를 뽑고, 문서세트 규칙을 코드로 검사하는 것이 Phase 1이다.
